# 修复画布对 Cloudflare R2 的存储能力检查

## 目标与背景

修复 Narra Image 画布的存储能力检查，使配置了官方 Cloudflare R2 的部署能够通过启用画布后的 Node / Go 检查。

用户在确认诊断后明确要求直接在本仓库修复。原版本 `64dad3c` 的 Node 和 Go 都强制调用 R2 未实现的 `GetBucketVersioning`。2026-11-01 的只读诊断中，同一部署的 `HeadBucket` 返回 200，`GetBucketVersioning` 返回 403；数据库迁移已经完成。当前任务为源码修复，不包含生产发布或修改线上功能开关。

## 需求

- R1：Node 上传前检查与 Go readiness / GC 领取前检查使用一致的 R2 识别和验证规则。
- R2：只有通过 HTTPS 连接官方 R2 账户端点，并且对确切 bucket 的带认证只读探测成功，才能证明 R2 存储可用。不能仅凭 URL、SDK 空字段、403 或不支持错误放行；R2 探测必须拒绝重定向。
- R3：普通 S3 保留现有有界原始 XML 与版本检查语义；启用版本、暂停版本、未知状态、权限错误、超时均不得被误认为无版本存储。
- R4：保留 location 身份、原图登记与根保护、迟到版本回执隔离、精确 key 删除、计账与默认关闭的功能开关。无需数据库迁移或凭据变更。
- R5：保留用户已有 `.gitignore` 与 `.serena/project.yml` 修改。仓库已从 `1f7948e` 快进到与部署一致的 `64dad3c`。
- R6：验证中发现 Windows CRLF shebang 触发 Vite SSR 的五个 Canvas 测试套件加载失败。仅为三个明确脚本固定 LF，保留与 Git 基线一致的脚本内容及全部原断言，不修改全局 Git 设置。

## 验收标准

- [x] 真实 SDK + 模拟传输证明官方 R2 只发起一次带签名的 HeadBucket，成功后 Node / Go 存储检查均通过。
- [x] 共享端点场景覆盖默认与 eu / fedramp / us 端点、规范化、伪装域名、HTTP、非默认端口和非法 location；两端结果一致。
- [x] R2 探测拒绝失败、意外状态、版本相关响应头、超时与取消；普通 S3 的 XML / 版本状态反例继续通过。
- [x] 相关画布、readiness 和 GC 测试通过；类型、lint、Go vet / build 验证完成，不能执行的基础设施检查明确留档。
- [x] README 与存储契约说明新的 R2 验证方式及部署仍需显式启用开关。

## 范围外

不发布远端、不重启生产容器、不修改凭据权限、不执行真实对象写入或删除、不进行付费生成、不更改画布 UI、数据库或 GC 保留期限。
