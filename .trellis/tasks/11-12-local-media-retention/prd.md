# 服务器图片存储与 5GB 清理管理

## 目标与用户价值

控制本站图片存储的持续增长，减少对 Cloudflare R2 免费额度的依赖。提供服务器持久化文件存储，以及网页中的用量查看、一键清理、定时清理和容量自动清理；PostgreSQL 保存媒体元数据。

## 已确认范围

- 用户于 2026-11-12 同意按“本地文件存储 + PostgreSQL 元数据 + 网页清理管理 + 5GB 容量控制”创建任务并规划。
- 用户明确“目前没有视频渠道可以用，先做图片的就好”：覆盖生成图片、普通上传参考图和画布导入图片；视频文件及视频专用封面不迁移、不计入本轮额度、不进入清理候选。
- 本任务拥有完整要求、子任务边界和最终集成验收；用户在最终规划摘要后回复“没问题”，已批准三个图片子任务的实施。生产数据迁移、删除与部署不包含在代码实施授权中。

## 仓库事实

- 数据库已经使用 PostgreSQL：`prisma/schema.prisma:6`。现有生成图片/视频保存 URL、存储类型、对象 key，但没有统一的物理文件计量清单：`prisma/schema.prisma:544`、`prisma/schema.prisma:569`。
- Go Worker 的生产图片和视频结果依赖 S3/R2；图片 data URL 回退仅允许开发环境：`worker/internal/worker/storage.go:100`、`worker/internal/worker/storage.go:166`。
- Node 也有参考图持久化入口，不能只修改 Worker：`src/lib/storage/persist-generated-image.ts:118`。
- 画布导入素材已有字节计量、上传状态及引用保护：`prisma/schema.prisma:618`；其 GC 只处理登记过、无引用并满足七天宽限期的导入文件，不能直接用它清理生成作品：`.trellis/spec/operations/canvas-contracts.md:42`。
- dedicated Compose 的 app 与 Worker 分离，当前只挂载数据库卷；新增本地存储必须解决共享持久化目录：`docker-compose.yml:66`、`docker-compose.yml:102`、`docker-compose.yml:134`。

## 需求

| 编号 | 要求 |
| --- | --- |
| R1 | 提供可用于生产的本地持久化文件存储；PostgreSQL 记录定位、归属、大小和生命周期，重启/更新不丢文件。 |
| R2 | 管理网页显示已用量、预留量、容量上限、文件数量、可清理量和最近清理结果；管理员才能修改全站清理策略。 |
| R3 | 一键清理先展示范围与预计释放量，经确认执行实际文件删除；结果区分成功、跳过和失败，历史页面能识别已清理文件。 |
| R4 | 支持可配置保留期限与后台定时清理，浏览器关闭不影响执行；重复触发和多个 Worker 不重复删除或重复扣减空间。 |
| R5 | 全站受管理图片额度初始为 5GB（5,000,000,000 字节）；包含已登记物理副本与尚未物化的并发预留，空间不足时按最旧的可清理内容依次回收，不能仅靠定时扫描控制上限。 |
| R6 | 保护精选作品、有效画布/任务/站点封面引用及在写文件；保留现有画布导入素材的引用与七天宽限契约；可清理量不足时返回明确容量不足结果。 |
| R7 | 空间释放以文件删除已确认为准；失败、超时或结果未知不得虚报回收成功；重启后能够恢复未完成工作。 |
| R8 | 历史 R2 图片继续可访问；提供可预览、可恢复、可验证的迁移方式，不能仅改配置就令历史图片断链；同一清理规则可作用于已登记的 R2 对象。 |
| R9 | 保留生成任务的状态、提示词和扣费/退款记录；清理媒体不伪造任务失败、不再次生成、不再次扣费。 |

## 清理行为与默认值

这些参数和可见行为一并提交最终审阅，具体技术实现位于 `design.md`。

| 项目 | 行为 |
| --- | --- |
| 容量回收 | 启用存储管理后按 5GB 上限执行；生成/上传并发预留也占额度。预留不足时只回收到本次所需空间；受保护内容占满时暂停新增并解释原因。 |
| 生成预算 | 上游生成前预留有界输出预算，结果保存后退回未使用部分；预算可能比最终文件大，所以容量清理可能比按最终文件大小计算更早发生。 |
| 输出边界 | 统一生成结果最大为单图 50MiB、每次最多请求的 1–4 张；保留 Canvas/外部参考图已有的更小输入限制。超大 b64 与远端结果采用一致边界。 |
| 定时回收 | 提供开关，默认关闭；开启时初始为每 24 小时清理超过 30 天的可清理图片，周期与天数可修改。 |
| 一键回收 | 先按选定天数预览；可以显式改为全部可清理历史图。执行受本次预览范围约束，不能把随后新写入的图加进来。 |
| 年龄与容量 | 保留天数是年龄筛选；达到容量上限时，可以回收未满该天数的普通历史图。引用保护、在写保护和 Canvas 七天宽限始终优先。 |
| 历史展示 | 图片清理后显示“图片已清理”，保留任务和提示词；下载/复用入口不继续请求已经删除的文件。 |
| 旧存储启用 | 更新版本不会立即批量删除旧 R2 文件；先盘点已知图片和引用，再明确启用管理策略。来源不明的图片单独标记待核实。 |
| 迁移 | 先预览和校验；默认保留源副本，删除旧 R2 源是独立明确选项。源/目标并存时都显示占用，不能把复制成功当作空间已释放。 |

## 验收标准

- [x] A1 → R1：在未配置 S3 的本地存储测试部署中，新图片生成、参考图上传、画布导入、查看和下载正常；容器重启/重建后仍可读取。
- [x] A2 → R2/R3：管理员看见真实用量并完成预览、确认、清理、结果查看；普通用户不能执行全站清理。
- [x] A3 → R4：浏览器关闭时调度仍执行；同一次任务重复提交或多个 Worker 同时处理不会重复计量。
- [x] A4 → R5：使用小额度夹具复现接近上限的并发写入，优先回收最旧可清理文件，容量包含在途预留，不因竞争越界。
- [x] A5 → R6：精选、画布/任务/站点封面所需素材、写入中对象及仍在宽限期内的画布导入素材不会被清理；受保护文件占满额度时新增失败且原因可见。
- [x] A6 → R7/R9：删除失败和进程重启不会虚减用量；成功清理后历史记录仍在并显示已清理状态，任务/计费事实保留。
- [x] A7 → R8：混合本地/R2 的历史图片可读取；迁移验证通过前不切换读取位置；中断可重入且不会误删未登记对象。
- [x] A8 → R1/R8：embedded 与同一服务器上的 dedicated 部署均有本地持久化的验证证据；历史 S3 行为保持兼容。
- [x] A9 → R1/R5/R8：含视频、视频专用封面及第三方图片的夹具中，仅本轮确定的受管理图片会被计量、迁移和清理；未纳管条目明确显示，不能谎报全桶已盘点。
- [x] A10 → R5/R9：容量不足时能在上游调用前拒绝；大小/数量异常、部分写入与持久化失败不导致重复上游生成，且保留当前不同契约版本的退款规则。

## 当前不包含

- 视频存储、视频播放/下载改造、视频文件及视频专用封面的迁移与清理。
- 将整张图片以 base64 或二进制作为 PostgreSQL 的主要存储。
- 改换数据库、改动提示词/生成计费业务，或直接连接生产系统执行迁移、清理、部署。
- 跨多台主机的本地目录复制与分布式文件系统维护。
- 根据 URL 前缀或整个 bucket 的内容推断归属后批量删除未知文件。
- 修改当前图片链接的访问权限模式、为点赞增加“永久收藏”含义，或承诺删除源对象后仍能访问站外复制的原 R2 链接。
- 将数据库、日志、缓存和整个服务器磁盘空间包含在 5GB 原图额度保证中。
