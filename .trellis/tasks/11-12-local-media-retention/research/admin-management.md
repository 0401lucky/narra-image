## 建议的最小管理能力

1. 路由建议为 `/admin/settings/storage`，展示当前后端、本轮纳入管理的媒体类型、已用/预留/额度/可清理量、数量和最近执行结果。磁盘剩余空间与媒体额度是不同指标，不能混报。
2. 配置保留期限、调度周期、容量额度；保存后显示明确的下一次执行信息。策略保存在数据库，Worker 在有界周期内读取；环境变量只描述后端、凭据、持久化目录等部署配置。
3. 清理预览展示候选数量、估算字节、受保护量及跳过原因。预览绑定策略版本与候选快照；执行逐对象重新校验引用/状态，期间新写入不能被悄悄加入原确认范围。
4. 确认后创建持久清理任务，API 返回任务 ID；网页轮询进度。浏览器断开不终止已提交的任务，重复确认复用幂等身份。
5. 后台只累计已经确认物理删除的对象与字节；部分失败应明确显示“部分完成”及可重试状态，不把请求受理等同于空间释放。
6. 清理后的历史作品保留提示词、时间与任务记录，展示“图片已清理”，不可继续下载或拿不存在的文件作为参考图。媒体 tombstone 应进入正式 DTO，避免前端靠请求图片失败猜测。

## 需要避免的混用

- `BenefitConfig`/`LoginCoverConfig` 的普通 upsert 不能直接替代带并发约束的全站容量预留。
- 现有同步 HTTP 管理操作最多等待数分钟，新批量清理不能要求用户一直保持连接；队列/任务状态应持久化。
- 5GB 是文件额度，并不证明整个磁盘占用小于 5GB；数据库、日志、应用缓存、迁移双份与临时数据应有独立说明和工作区界限。
- 在 UI 配置里启用定时清理不应悄悄扩大候选类型；用户已明确视频及视频专用封面不纳入此次图片额度和清理。

## 后续验证建议

- 实际渲染管理页面并验证鉴权、用量加载、策略保存、预览、确认、取消、执行中刷新、失败重试与完成状态。
- 集成验证同一清理请求重放、多个 Worker 竞争、预览后引用变化、进程重启与删除失败，结合真实临时目录/模拟 S3 确认释放量。
- 触及 runtime 配置、Worker、schema 与画布时按对应 operations spec 运行契约/数据库/部署验证；规划阶段不运行产品测试来冒充实现验收。
